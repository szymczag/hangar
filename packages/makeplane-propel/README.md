# @makeplane/propel 0.9.7 (recovered source)

This package is the TypeScript source of the npm package `@makeplane/propel` at
version 0.9.7, the React component library that upstream Plane v1.5.0 builds its
new interface on. Upstream publishes only the compiled `dist/`; its source
repository is private. Hangar recovers the source from the published tarball,
builds it with its own toolchain, and checks that the result is equivalent to
what upstream published.

No Hangar application depends on this package yet. Whether Hangar adopts the
upstream redesign is a separate decision; this package exists so that decision
can be made on reviewable source, and so Hangar can provide the Corresponding
Source (AGPL-3.0 §6) for anything it ships that contains this code.

The package keeps the upstream name, `@makeplane/propel`, so upstream imports
resolve unchanged. It is `private` and is never published.

`RECOVERY.json` records the integrity and, for every file under `src/`, its
SHA-256, how it was obtained and which published files it came from.

## How the source was recovered

`scripts/propel/recover.mjs` does the whole recovery; nothing under `src/` was
written by hand. It refuses to run when the tarball's sha512 differs from the
expected one, when two inputs map to the same path, when a source map lacks
`sourcesContent`, when a re-export file has a shape it does not know, or when any
relative import in the result does not resolve to a recovered file.

| Origin             | Files | What it is                                                                                                                                                                                                                  |
| ------------------ | ----: | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sourcemap`        |  1684 | Every emitted JavaScript module has a source map whose `sourcesContent` holds its original file. Written out verbatim.                                                                                                      |
| `barrel`           |   129 | The `index.ts` re-export modules. They contain no code, so the bundler wrote no source map; their exports are read back from the emitted `index.js` (values) and `index.d.ts` (types).                                      |
| `dts`              |     2 | `src/internal/variant-props.ts`, a type-only module, rebuilt from its declaration file; `src/components/menu/menu-footer.ts`, a re-export the JavaScript graph dropped, rebuilt from its declaration file.                  |
| `inlined-constant` |     1 | `src/internal/dropdown-edge-gap.ts`. The bundler inlined `DROPDOWN_EDGE_GAP_PX` into its seven users and emitted nothing for the module; the script reads the value (16) back from every user and refuses if they disagree. |
| `copied`           |     8 | The three Tailwind v4 stylesheets (published unprocessed), the four logo-spinner images, and `LICENSE`.                                                                                                                     |

The 1684 verbatim files are upstream's code as upstream wrote it. The 132
rebuilt files are re-export lists, one type alias and one constant; where their
exact form is not visible in the output (for example the order of a barrel's
statements, or `.ts` rather than `.tsx`), the script chooses the form that
reproduces the published output, and the equivalence check below is what proves
the choice.

The 934 icon components under `src/icons/` say they were generated by
`scripts/generate-icons.mjs`. That generator and its SVG inputs were not
published, so the generated TSX is the preferred form for modifying them and is
treated as their source. Upstream published no tests or stories either.

## Rule: recovered files are never edited

`src/` stays exactly as the recovery wrote it. `tests/recovery.test.mjs` fails
if any file under `src/` differs from its SHA-256 in `RECOVERY.json`, or if a
file is added or removed, and CI re-runs the recovery from the npm tarball and
diffs the result against the committed tree. If Hangar ever needs to change
this code, the change goes into a separate, visible file or patch, not into
`src/`. Formatting, linting and the branding check skip `src/` for the same
reason.

## Building

```sh
pnpm --filter @makeplane/propel build      # writes dist/
pnpm --filter @makeplane/propel check:types
pnpm --filter @makeplane/propel test       # RECOVERY.json hashes
```

The toolchain follows the package's own published `devDependencies`, pinned
exactly and only for this package (the rest of the repository keeps its catalog
versions):

Pinned by a `tsdown@0.22.14>rolldown` override: 1.2.1 to 1.2.12 stop inlining single-use constants inside functions, and 1.2.13 emits re-export barrels as `export … from` instead of `import` plus `export`; only 1.2.0 matches the published output |

| @base-ui/react             | 1.8.0                | the newest release before 0.9.7 was published and the version upstream v1.5.0 resolves; the declarations are generated against its types. `tsdown.config.ts` was inferred from the output: unbundled ESM (one file per
module), no syntax lowering, source maps and declaration maps, the
`"use client"` banner on every file except the icon components (which get an
empty banner, as published), the logo-spinner images left as external imports
and copied next to their module, and the stylesheets copied as they are. The
entry points are the `index.ts` of every directory under `base/`, `elements/`,
`components/` and `hooks/`, in that group order and sorted, then `icons/`: the
order fixes the bundler's module execution order, which shows in the order of
import statements. `package.json` declares `"sideEffects": ["**/*.css"]` and
copies the `exports` map from the published package unchanged.

## Equivalence with the published package

```sh
pnpm --filter @makeplane/propel build
node scripts/propel/compare-dist.mjs --built packages/makeplane-propel/dist \
  --tarball makeplane-propel-0.9.7.tgz \
  --integrity "$(node -p 'require("./packages/makeplane-propel/RECOVERY.json").integrity')"
```

The comparison checks the file set (maps included), JavaScript as syntax trees
with every comment that carries meaning (pure annotations, JSDoc), the
`sources` and `sourcesContent` of every source map, declarations as text, the
exported names of all 130 public entry points, and stylesheets and images byte
for byte. At the time of recovery:

| Kind              | Files | Byte-identical | Accepted difference                                                     |
| ----------------- | ----: | -------------: | ----------------------------------------------------------------------- |
| JavaScript        |  1813 |           1805 | 8 import order                                                          |
| Declarations      |  1749 |      1721–1744 | 5–28 literal union member order, varying by run (see below)             |
| Source maps       |  3302 |           3301 | 1 (`variant-props.d.ts.map`: same source, mappings of the rebuilt file) |
| Styles and images |     7 |              7 | none                                                                    |

Only two kinds of difference are accepted, and the script fails on anything
else:

- **Import order (8 component modules).** The same import declarations with
  the same bindings in a different order; the module bodies are identical. The
  order follows the bundler's execution order across the whole build, which
  depends on statement order inside barrels that were never published. No
  module does anything at load time beyond creating its own values (cva class
  builders, React contexts, `displayName` on its own components), so the order
  its dependencies are evaluated in cannot change behaviour.
- **Literal union order (5 to 28 declaration files, varying by run).** For example
  `"sm" | "md" | "xs"` printed as `"xs" | "sm" | "md"`. TypeScript prints a union
  in the order it first created each literal type, and the declaration plugin
  emits modules in the order they finish loading, which is not deterministic:
  repeated identical builds here produced between 5 and 28 such files, and the
  published build was subject to the same effect. A union is unordered, so the
  types are the same.

## Updating to a new upstream version

1. Fetch the tarball: `npm pack @makeplane/propel@<version>`. Take the expected
   integrity from the upstream `pnpm-lock.yaml` of the release that uses it, and
   check that the tarball matches.
2. Recover into the package:
   `node scripts/propel/recover.mjs --tarball makeplane-propel-<version>.tgz --integrity <sha512-…> --out packages/makeplane-propel`.
3. Update `package.json` (version, `dependencies`, `peerDependencies`, `exports`)
   and the toolchain pins from the new tarball's `package.json`.
4. Review `git diff packages/makeplane-propel/src` as ordinary code, with a
   security review. This is the point of the exercise: a reviewable source diff
   instead of a `dist/` diff.
5. Build and run `compare-dist.mjs`. Any difference outside the two accepted
   kinds must be fixed in the build configuration or explained before the update
   merges.
6. Update `NOTICE.md`, this README and the CI tarball reference.
