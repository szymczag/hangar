# Amazon SES email operations

Status: production configuration and maintenance runbook.

Last reviewed: 2026-07-14.

This how-to configures Hangar to submit raw MIME through the Amazon SES v2 API in Europe (Frankfurt), consume feedback through SNS and SQS, use a dedicated sending subdomain, and maintain deliverability. Hangar authenticates to AWS with workload identity or scoped API credentials and sends through the regional HTTPS endpoint.

Read [Email delivery and OpenPGP](email-delivery-and-openpgp.md) before rollout. The controller must separately approve the provider agreement, transfer assessment, subprocessors, retention, transparency, and incident procedures. This runbook is not legal advice.

The rollout is feature-gated. With durable delivery disabled, Hangar continues to use its direct transport compatibility path and does not create anti-phishing receipts. Turn the feature on only as part of the Helm deployment described below; the dedicated worker, encryption keys, SES feedback path, and database migrations must become available together.

Every value below is reserved example data. Replace domains, account IDs, ARNs, queue URLs, role names, addresses, and DNS tokens outside Git. Do not add production values to this document.

## Target topology

| Purpose                              | Example                                                           |
| ------------------------------------ | ----------------------------------------------------------------- |
| Region                               | `eu-central-1`                                                    |
| SES identity and visible From domain | `hangar.example.com`                                              |
| Sender                               | `Hangar <hello@hangar.example.com>`                               |
| Monitored Reply-To                   | `support@example.com`                                             |
| Custom MAIL FROM                     | `bounce.hangar.example.com`                                       |
| Auth configuration set               | `hangar-auth`                                                     |
| Notification configuration set       | `hangar-notifications`                                            |
| Delivery                             | Hangar mail worker → SES v2 `SendEmail` raw MIME over HTTPS       |
| Feedback                             | SES → SNS → encrypted SQS → Hangar mail worker                    |
| Authentication                       | Kubernetes workload identity; static access keys only as fallback |
| Tracking                             | Open and click tracking disabled                                  |
| Archiving                            | Disabled                                                          |

Keep SES, SNS, SQS, CloudWatch alarms, and any customer-managed KMS keys in the same selected region. Do not use a global SES endpoint or copy feedback data to another region without a separate review.

## 1. Prepare the domain

Use a transactional subdomain rather than the organizational domain used by Google Workspace or human mail. This isolates sending reputation and authorization. Do not change the organizational domain's Google MX records.

In the SES console for `eu-central-1`:

1. Create a domain identity for `hangar.example.com`.
2. Enable Easy DKIM with 2048-bit keys.
3. Publish the three exact CNAME records generated by SES.
4. Wait for both identity verification and DKIM status to succeed.
5. Do not create a narrower address identity that overrides the domain's inherited signing settings.

### Custom MAIL FROM and SPF

Configure `bounce.hangar.example.com` as the identity's custom MAIL FROM domain. Select **Reject message** if the MAIL FROM MX becomes invalid; falling back to an `amazonses.com` MAIL FROM would hide broken alignment.

Publish the exact region-specific MX and one SPF TXT record:

| Name                        | Type | Example value                                 |
| --------------------------- | ---- | --------------------------------------------- |
| `bounce.hangar.example.com` | MX   | `10 feedback-smtp.eu-central-1.amazonses.com` |
| `bounce.hangar.example.com` | TXT  | `v=spf1 include:amazonses.com ~all`           |

Do not publish Google MX records at this host. Do not create multiple SPF TXT records at the same name. Wait for the SES MAIL FROM status to become successful.

### DMARC

Publish a policy for the sending subdomain, initially in reporting mode:

```text
Name:  _dmarc.hangar.example.com
Type:  TXT
Value: v=DMARC1; p=none; rua=mailto:dmarc-reports@example.com; fo=1; adkim=s; aspf=r; pct=100
```

Use a controlled reporting mailbox or reviewed DMARC service. Reports contain metadata and need their own access and retention rules.

Easy DKIM should sign with `d=hangar.example.com`, satisfying strict DKIM alignment. The custom MAIL FROM subdomain satisfies relaxed SPF alignment. After at least two representative reporting cycles with no unknown legitimate sender, move deliberately to `p=quarantine`; observe again, then move to `p=reject`. Do not advance while alignment or legitimate-source inventory is unresolved.

## 2. Leave the SES sandbox

SES sandbox status and quotas are regional. Verify DNS and the feedback path first, then request production access for `eu-central-1` as transactional email.

Describe the real program:

- account mail is initiated by a user action;
- project notifications go only to known users;
- confidential notifications are held until the user verifies an OpenPGP key;
- hard bounces and complaints are consumed and suppressed;
- users control notification preferences; and
- an operator monitors reputation and abuse.

Request a measured quota. Do not inflate expected volume. Use the SES mailbox simulator while sandboxed and for recurring failure-path tests; simulator outcomes do not damage reputation metrics.

## 3. Create configuration sets

Create `hangar-auth` and `hangar-notifications` in `eu-central-1`.

For both:

- enable reputation metrics;
- require TLS for provider delivery if that matches the organization's confidentiality policy;
- use the shared IP pool initially;
- enable account-level suppression for hard bounces and complaints;
- disable open and click tracking;
- disable message archiving; and
- do not enable engagement tracking through another feature.

Use a short maximum delivery duration for `hangar-auth`, shorter than the validity of its magic codes. Use a documented service objective for notifications. Hangar passes the selected configuration-set name and opaque tags as structured SES API parameters.

## 4. Build the feedback path

Create these resources in `eu-central-1`:

1. an SNS topic used only for Hangar SES events;
2. an SQS dead-letter queue with server-side encryption and 14-day retention;
3. a primary SQS queue with server-side encryption, four-day retention, long polling, a visibility timeout of at least 120 seconds, and redrive to the dead-letter queue; and
4. an SNS subscription from the exact topic to the primary queue.

Use an AWS-owned SQS key or configure all required KMS grants for SES/SNS and the consumer. Restrict the SNS topic policy to SES in the expected account and region. Restrict the primary queue policy so only the exact SNS topic can call `sqs:SendMessage`.

Add an SNS event destination to both configuration sets for:

- send;
- delivery;
- bounce;
- complaint;
- reject;
- delivery delay; and
- rendering failure.

Do not enable open, click, or subscription events. Raw events can contain personal routing metadata. Hangar validates topic, account, event type, opaque outbox tag, and provider Message-ID; it persists only bounded metadata and never logs the raw event.

Invalid messages remain for SQS redrive. Alert on any dead-letter message and inspect it only in a restricted operational workflow.

## 5. Create the workload identity

The chart runs sending and feedback consumption in a dedicated `mail-worker` deployment and Celery queue. Grant its Kubernetes service account one narrowly scoped AWS role. On EKS, use IRSA or the organization's approved EKS Pod Identity pattern. Other Kubernetes environments need their platform-specific workload-identity binding.

An example IAM policy shape is:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SendHangarEmail",
      "Effect": "Allow",
      "Action": "ses:SendEmail",
      "Resource": [
        "arn:aws:ses:eu-central-1:123456789012:identity/hangar.example.com",
        "arn:aws:ses:eu-central-1:123456789012:configuration-set/hangar-auth",
        "arn:aws:ses:eu-central-1:123456789012:configuration-set/hangar-notifications"
      ],
      "Condition": {
        "StringLike": {
          "ses:FromAddress": "*@hangar.example.com"
        },
        "Bool": {
          "aws:SecureTransport": "true"
        }
      }
    },
    {
      "Sid": "ConsumeHangarEmailEvents",
      "Effect": "Allow",
      "Action": ["sqs:ReceiveMessage", "sqs:DeleteMessage", "sqs:ChangeMessageVisibility", "sqs:GetQueueAttributes"],
      "Resource": "arn:aws:sqs:eu-central-1:123456789012:hangar-mail-events"
    }
  ]
}
```

Validate the final policy with the actual resources. It must not grant SES administration, identity changes, arbitrary SQS access, queue sending, SNS administration, S3 access, or wildcard service permissions.

For IRSA, annotate only the mail service account:

```yaml
mail:
  serviceAccount:
    create: true
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/hangar-mail-worker
```

Restrict node-instance metadata so pods cannot fall back to a broad node role. The API, web, admin, default worker, beat worker, and migration job do not need the SES/SQS identity.

### Static-credential fallback

If workload identity is unavailable, create independent programmatic credentials and store them only in the deployment secret. Use the chart's optional `EMAIL_SES_AWS_*` and `EMAIL_EVENTS_AWS_*` mappings. Never use a human administrator's key, an SES SMTP password, object-storage credentials, or a credential shared with another application.

Rotate static credentials by creating the replacement, updating the secret, restarting the mail worker, completing a controlled send and feedback test, then revoking the old key. Workload identity is preferred because it avoids this lifecycle.

## 6. Configure the Helm release

Use deployment-specific values outside the repository:

```yaml
mail:
  enabled: true
  provider: ses_api
  sender: "Hangar <hello@hangar.example.com>"
  replyTo: "support@example.com"
  messageIdDomain: hangar.example.com
  ses:
    region: eu-central-1
    accountId: "123456789012"
    authConfigurationSet: hangar-auth
    notificationConfigurationSet: hangar-notifications
    eventsQueueUrl: https://sqs.eu-central-1.amazonaws.com/123456789012/hangar-mail-events
    eventsTopicArn: arn:aws:sns:eu-central-1:123456789012:hangar-mail-events
  openpgp:
    enabled: true
  auditRetentionDays: 90
  serviceAccount:
    create: true
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/hangar-mail-worker
```

The chart enables policy-aware delivery, creates a dedicated mail worker, routes encrypted notifications and feedback tasks to its queue, permits HTTPS egress, and fails schema validation for incomplete production mail values.

Before applying:

```bash
helm lint charts/hangar
helm template hangar charts/hangar -f <deployment-values.yaml> > /tmp/hangar-rendered.yaml
```

Review the rendered service account, mail-worker environment, network policy, secret references, and image security context. Do not commit the rendered file if it contains deployment identifiers.

## 7. Validate before real traffic

Complete all checks with controlled recipients:

- a minimal cleartext account message has the security notice and receipt;
- its outbox receipt contains no subject, body, attachment, or authentication token;
- a confidential message with no verified key is suppressed and remains in-app;
- an encrypted test is valid RFC 3156 PGP/MIME and decrypts in every supported client;
- the real subject, body, attachment, and receipt are inside encryption;
- the database contains only PGP/MIME ciphertext for a queued protected notification;
- the outer subject is generic and no remote tracking is inserted;
- DKIM, SPF, and DMARC pass and align;
- SES events move through SNS/SQS and update the same outbox receipt;
- hard bounce and complaint simulations create local suppressions;
- a transient bounce does not create permanent suppression;
- an invalid SQS message reaches the dead-letter queue;
- the admin ledger shows status without message content;
- the user can find the exact receipt in Profile → Security; and
- restarting a worker does not duplicate an accepted message.

Inspect the raw MIME source, not only the mail client's rendered view. Test Thunderbird, the approved command-line workflow, and the actual Workspace/Gmail workflow expected by users.

## 8. Maintain deliverability

### Continuous monitoring

Alert on:

- SES account health, reputation warnings, send quota, and throttling;
- hard-bounce rate approaching 5%; use a stricter internal early-warning threshold;
- complaint rate approaching 0.1%; use a stricter internal early-warning threshold;
- any SES account review or pause warning;
- SQS age of oldest message, visible message count, and dead-letter count;
- Hangar `failed_permanent`, `acceptance_unknown`, and old due-row counts;
- unexpected growth in local suppressions;
- DKIM verification or custom MAIL FROM failure;
- DMARC unknown sources or alignment failure;
- expiring user OpenPGP keys; and
- mail-worker crashes, retries, or inability to assume its workload role.

The numerical bounce and complaint values above are outer safety boundaries from SES guidance, not operational targets. Healthy transactional traffic should be materially lower.

### Sending practice

- Send only transactional messages caused by a user or project event.
- Never buy, rent, scrape, or import marketing lists into this path.
- Validate addresses at entry and stop immediately after a hard bounce or complaint.
- Keep From name, domain, layout, and purpose consistent.
- Use a monitored Reply-To instead of a `no-reply` dead end.
- Preserve separate auth and notification configuration sets.
- Ramp a new subdomain gradually with real, wanted traffic; avoid a sudden unrepresentative burst.
- Do not add marketing campaigns to this subdomain or AWS account without a separate reputation design.
- Keep links on controlled HTTPS domains and avoid redirector chains.

### Weekly review

Review SES reputation, CloudWatch alarms, DMARC aggregate reports, SQS/DLQ state, Hangar's admin delivery ledger, suppression decisions, provider failures, and current sending volume. Investigate changes, not just absolute thresholds.

### Monthly review

Confirm DNS records, identity/DKIM/MAIL FROM status, workload-role policy, queue/topic policy, secret access, retention jobs, alarm recipients, production quota, supported client compatibility, and operator access. Sample recent receipts without accessing message bodies.

### Suppression recovery

Never remove a complaint or hard-bounce suppression merely because a user asks to “try again.” Verify that the address was corrected or the provider outcome was a false positive, check the SES account-level suppression state, record the operator reason in Hangar, and send one controlled account message. A new permanent event automatically reactivates local suppression.

## Incident procedures

### Queue backlog

1. Pause nonessential notification producers if the backlog is growing.
2. Check mail-worker health, RabbitMQ, AWS identity, SES quota, SQS permissions, and regional status.
3. Inspect status counts and age, never raw payloads unless incident authority requires it.
4. Scale the mail worker cautiously; SES quota still applies.
5. Let the durable dispatcher recover due rows. Do not bulk-reset accepted or acceptance-unknown rows.

### High bounce or complaint rate

1. Stop the affected notification class or all non-account sending.
2. Confirm local and SES suppression are active.
3. Identify the source workflow using opaque policy/configuration-set metrics.
4. Correct address collection, consent, stale recipient, or content problems.
5. Resume with a small controlled volume and monitor continuously.

### Suspected credential or role compromise

1. Remove the role binding or revoke static credentials.
2. Stop the mail worker.
3. Review CloudTrail for SES and SQS actions and SES sending metrics.
4. Rotate affected credentials and application encryption keys according to their separate procedures.
5. Preserve evidence and follow the security and data-protection incident process.
6. Re-enable only after a controlled send, feedback, and policy test.

### `acceptance_unknown`

Do not automatically resend. SES may already have accepted the message. Wait for a correlated SES event, check the provider Message-ID and logs available under incident authorization, and use the account action's normal user retry only if the original token remains safe and product behavior permits it.
