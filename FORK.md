# Hangar — fork maintenance guide

Hangar is a fork of [makeplane/plane](https://github.com/makeplane/plane) (AGPL-3.0) that
implements additional features on top of the open-source core: hardened federated
SSO (Google, OIDC, and SAML 2.0), Epics, custom issue types with custom properties,
time tracking (worklogs), secure email/OpenPGP delivery, and the default-off Runner
installation control plane, and Todoist CSV imports.

All fork code is isolated so upstream syncs stay cheap:

- **Backend** lives in the dedicated Django app `apps/api/plane/ext/` (own models,
  migrations, serializers, views, URLs). Upstream never touches this path.
- **Frontend** lives in the `apps/web/ce/` overlay, resolved via the `@/plane-web/*`
  alias (`apps/web/tsconfig.json`). Filling existing CE stubs requires no core edits.
- Everything else is an **append-only** edit to a core file, tracked in the ledger below.

## Syncing with upstream

```sh
git remote add upstream https://github.com/makeplane/plane.git   # once
git fetch upstream
git merge upstream/preview       # merge, never rebase — fork history is published
```

After every sync, walk the ledger below and re-verify each touchpoint still applies.

### Upstream maintenance loop

Upstream security fixes reach Hangar through one loop, so none depends on someone
remembering to look:

1. **Watch.** The weekly `Upstream watch` workflow
   (`.github/workflows/upstream-watch.yml`) compares upstream with `UPSTREAM_BASE.json`:
   stable releases newer than `package_version`, and repository security advisories
   published on or after `synced_at` or fixed only in a published release newer than
   `package_version` (so an older advisory a later release fixes stays listed when
   `synced_at` moves). It keeps exactly one open issue labelled
   `upstream-sync` listing them, comments when the list changes, and closes the issue
   once the baseline covers everything.
2. **Assess.** For each advisory, decide whether Hangar is affected: the code may be
   upstream-only, already fixed here, or reshaped by a fork touchpoint in the ledger
   below. Record the reasoning on the issue.
3. **Fix.** Either sync upstream (the merge above) or, when a full sync is not yet
   practical, backport the targeted fix. A backport always lands with a regression test
   that fails without it; per-advisory SSRF coverage, for example, is mapped in
   `apps/api/plane/tests/unit/bg_tasks/test_ssrf_advisories.py`.
4. **Record.** Name each addressed advisory in the "Security and privacy" section of
   the next `docs/releases/<tag>.md`.
5. **Move the baseline.** The sync pull request updates `package_version` and
   `synced_at` in `UPSTREAM_BASE.json`; the next weekly run then drops what the sync
   covers and closes the issue once nothing is left. A backport alone does not move
   the baseline, so the issue stays open, with the assessment recorded on it, until a
   sync catches up.

**Syncs are signed squash commits.** `preview` requires signed commits and upstream's
commits are not signed, so an upstream release is absorbed as one signed squash
commit (v1.4.3 arrived as `eca57c46d1`, #348), not as a merge. Two things follow:

- `revision` stays the last upstream commit that is actually in Hangar's history
  (`917b23a6c16d`, v1.4.0). Release metadata and release notes check that it is an
  ancestor of the release commit (`release_metadata.py`, `release_notes.py`), which a
  squashed release never is. `package_version` and `synced_at` record what was
  absorbed; `revision` records the merge base Git can prove.
- Git's merge base with upstream never advances past that commit, so a plain trial
  merge of a newer release diffs upstream from v1.4.0 and replays the changes already
  squashed in. Pass the absorbed release as the base explicitly, so only what upstream
  changed since then is merged:

  ```bash
  git fetch upstream --tags
  base=$(git rev-parse "v$(jq -r .package_version UPSTREAM_BASE.json)^{commit}")
  git merge-tree --write-tree --merge-base "$base" HEAD v1.5.0
  ```

**Migrations keep Hangar's numbers.** Upstream migrations that Hangar already carries
are renumbered onto Hangar's chain, so a sync must not bring upstream's copies back:

- Converging with upstream v1.5.0, drop upstream's `db` migrations
  `0123_remove_apitoken_is_service_and_allowed_rate_limit`,
  `0124_intakeissue_intake_issue_snoozed_till_idx` and
  `0125_reset_project_deploy_board_identity`. Hangar ships them as `0135`, `0136` and
  `0134` (and upstream's `0122_alter_draftissue_…` as `0129`, dropped at the v1.4.3
  sync). Upstream migrations that Hangar does not carry yet are renumbered after
  Hangar's latest leaf, with their dependencies rewritten, never added under
  upstream's number.
- `apps/api/migrations_lockfile.txt` names the latest migration of every app with
  migrations (`db`, `ext`, `license`); `python manage.py makemigrations` rewrites it.
  `apps/api/plane/tests/unit/db/test_migrations_lockfile.py` fails on a stale lockfile,
  a second leaf in an app, or two migrations of one app sharing a number, and the
  `Migration check` workflow runs `makemigrations --check` against the merged graph,
  so a reintroduced upstream file fails CI rather than a deployment.

### Upstream changes not adopted

Upstream changes Hangar has decided not to take. A sync resolves their conflicts as
"ours" and keeps the reasons below current; reopening one is a separate decision.

- **Caddy for the web and admin frontends** (upstream effd0c5719,
  makeplane/plane#9716, in v1.5.0). Upstream replaced nginx with a Caddy build that
  runs as root and serves no Content-Security-Policy and no HSTS. Hangar keeps
  `nginx-unprivileged` (uid 101) with the generated CSP
  (`15-hangar-csp.envsh`, `packages/csp/nginx`), the security headers and the
  read-only-root Helm contract (ledger row 89); adopting Caddy would rewrite those
  controls and the chart's paths, uid and writable directories for no operator
  benefit. In a sync, resolve the modify/delete conflicts on
  `apps/{web,admin}/nginx/nginx.conf` as ours (keep the files), delete
  `apps/{web,admin}/caddy/`, and keep the Hangar `apps/{web,admin}/Dockerfile.*`
  and the AIO `COPY --from=web-img /usr/share/nginx/html` paths.
  Upstream's Caddyfile also limits each client IP to 300 static-file requests a
  minute. It is not ported to nginx: the frontends sit behind the bundled proxy, an
  ingress controller or a Gateway, so nginx sees the proxy's address, and keying on
  the client would need `real_ip` trust of a per-deployment proxy range (Compose
  network, Pod CIDR, Gateway data plane) that the image cannot know. Keyed on the
  proxy, one bucket would be shared by every user, while a single cold load of the
  code-split web app already fetches many chunks at once. Request rate limiting stays at
  the API (DRF throttles, `NUM_PROXIES`) and at the operator's edge.
- **The God Mode image-provider page** (upstream `apps/admin/app/(all)/(dashboard)/image/`
  and its "Images in Plane" sidebar entry, restyled in v1.5.0). It configures
  Unsplash, which Hangar removed (S21); the move of God Mode to Propel (row 159)
  keeps the route, the menu entry and `UNSPLASH_*` out. Upstream's admin
  `public/site.webmanifest.json` branding and its setup-form telemetry default
  (`is_telemetry_enabled: true`, S22) are not taken either, and the admin Caddy
  build is covered by the Caddy entry above.
- **Every property on the published boards** (upstream v1.5.0 `apps/space`,
  `getComputedDisplayProperties()` in the list and board roots). Upstream shows every
  work-item property on a public board, assignees included, so each card would carry
  member names and avatars to anyone with the link. The published boards keep the
  set Hangar has always shown: key, state, priority, labels and due date
  (`apps/space/helpers/display-properties.helper.ts`, row 164). The public API
  no longer returns `assignee_ids` or the project's member names either (S30,
  row 165, "Member data on published boards" below).
- **Issue types on the issue templates** (upstream 1d0ee2482a,
  makeplane/plane#9559). `type: Bug` / `type: Feature` need organization issue
  types, which a user-owned repository does not have; the deployment and version
  fields from the same change are taken in Hangar wording.
- **Weaker forms of security fixes Hangar already carries** (upstream v1.5.0
  backend). Where upstream and Hangar fixed the same issue differently, the backend
  keeps Hangar's stricter form; a sync resolves these as ours:
  `authentication/utils/oauth_state.py` (`validate_oauth_state`, makeplane/plane#10069)
  is not added, the OAuth callbacks keep the per-provider single-use transaction with a
  TTL (S11); `throttle_auth_redirect(is_admin=True)` (makeplane/plane#10059) is not
  taken, the decorator takes exactly one of `is_app`/`is_space` and the God Mode views
  keep `_throttled` (S8); `can_modify_asset` (makeplane/plane#10068) is replaced by
  `can_mutate_file_asset`, which answers 404; the external API's comment edit and
  delete stay with the author or a project admin, and the restricted-guest gate applies
  to workspace admins too (makeplane/plane#10016); workspace analytics stay limited to
  the caller's own projects (makeplane/plane#10065); `FileAssetSerializer` keeps every
  field read-only (makeplane/plane#10212); email notifications render comments as
  nh3-sanitized HTML (`sanitize_email_fragment`) rather than `striptags`
  (19d48d987c).
- **Member data on published boards** (upstream `apps/api/plane/space/`, all
  releases). Upstream's public board API returns every work item's `assignee_ids`
  and `created_by`, the project's member roster (`anchor/<anchor>/members/`), the
  first and last names of voters and reactors and the audit users of comments and
  of the board itself, to anyone with the link. Hangar names only the people who
  acted on the board, as display name and avatar (S30, ledger row 165), and the
  published boards render a mention as `@user`. In a sync, resolve
  `apps/api/plane/space/{views,urls,utils}/` and the Spaces member store as ours
  and keep the public serializers in `plane/space/serializer/public.py`.

### Vendored upstream packages

Upstream publishes some packages it builds on only as compiled npm tarballs.
Hangar keeps their source in the repository so it can review the code, build it
itself and provide the Corresponding Source for anything it ships.

- **`@makeplane/propel` 0.9.7** in `packages/makeplane-propel/`, the component
  library upstream v1.5.0's new interface is built on. Its source repository is
  private; `scripts/propel/recover.mjs` recovers the source from the tarball's
  source maps (verbatim) and rebuilds the barrels and three small modules the maps
  do not cover, refusing a tarball whose sha512 differs from the one upstream's
  v1.5.0 lockfile pins. The package builds with the toolchain the tarball names,
  pinned for this package only, and `scripts/propel/compare-dist.mjs` checks the
  build against the published `dist/` (`.github/workflows/propel-source.yml`).
  God Mode (`apps/admin`) is built on it since ledger row 159 and the published
  boards (`apps/space`) since row 164. Web (`apps/web`) loads the Propel tokens
  (`@plane/tailwind-config/propel.css`) and mounts the blocks toast viewport since
  row 169, and its shell (the root layout, sidebar, top navigation and app rail) is
  built on Propel since row 170, the command palette and the shared
  `components/{common,core}` since row 172, and the property dropdowns since row
  173 (the 1.4 module paths render them through compatibility shims until phase
  9), the sign-in, password and onboarding screens since row 174, and the
  projects list, project creation and the project settings pages since row 177,
  the workspace and account settings since row 178, the work item detail page and peek since row 182, the work item list layouts and their filters since row 184, the work item create and edit dialog, workspace drafts and the saved view lists since row 186, and cycles, modules, workspace analytics and intake since row 187; its other components stay on the 1.4 interface (`@plane/ui`,
  `packages/propel`) and move to Propel in phases.
  The recovered `src/` is never edited by hand; a bump re-runs the recovery and
  reviews the source diff. `packages/makeplane-propel/README.md` has the method,
  the equivalence report and the update procedure.
- **`@plane/blocks` 1.5.0** in `packages/blocks/`, upstream v1.5.0's composite
  components on top of Propel, taken whole from the v1.5.0 tag so a later sync is
  a plain diff. The one Hangar change: `src/auth/password/*` (the strength
  indicator) uses the fork's async zxcvbn policy from `@plane/utils`
  (`getPasswordStrengthResult`, `getPasswordCriteria(password, strength)`, 15
  characters, S9) instead of upstream's synchronous `getPasswordStrength`, and
  `@plane/blocks/auth` exports the `usePasswordStrength` hook it runs on (ledger
  row 156); and the emoji picker reads its data from this instance
  (`setEmojiDataUrl` in `@plane/blocks/emoji-icon-picker`, row 164), never from
  frimousse's default CDN. Its `@makeplane/propel` dependency is the workspace package (S27). God
  Mode is its first consumer (row 159), then the published boards (row 164) and web
  (row 169, toasts and the emoji data URL only); `src/icons` also carries Hangar's wordmark
  and mark (`HangarLogo`, `HangarMark`, row 160), so the screens moved off
  `packages/propel` keep the Hangar brand.

a conflict marker. Every control below has a test that fails if the control is removed

the same change. `.github/scripts/upstream_trial_merge.py` previews what a sync will
conflict on, grouped by conflict kind and by area, before any of it lands.
